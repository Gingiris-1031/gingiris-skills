# Multi-platform publication workflow

Use only when the user requests distribution across multiple platforms. The selected channels, voice, cadence, timezone and review process come from the current user/account context, not from a named operator's historical setup.

1. Reuse a source packet: original context, author, date, privacy, claim scope and permission. Keep source ownership intact in every adaptation.
2. Produce only requested platform variants. Adapt structure to the audience; do not require an image, carousel or fixed content-pillar mix for every post.
3. When media is useful, supply a reviewed asset or clearly marked storyboard. Verify platform-specific dimensions, length and publisher capability from current documentation before delivery; do not hardcode past connector request fields.
4. Read existing platform state and the local ledger. Use account + content/version + intended schedule as the duplicate key. A calendar-day limit applies only if the user approved that cadence.
5. Check public hosting authorization, actual URL accessibility and MIME type if the integration requires a URL. Prefer the configured native upload flow when available. Local existence alone is insufficient.
6. Within existing publication authorization, submit once, retain the returned ID and read back status. Pending/sending is not permission to resubmit. An error requires diagnosis; recovery cannot silently create duplicates.
7. Verify public text, links and intended media. Report partial success per platform. Unknown state remains unknown until reconciled.
8. Update the task ledger. Suggest useful review windows; create scheduled follow-up only if requested.

Separate content review (facts, attribution, voice, privacy, CTA) from delivery review (account, capability, media, schedule, receipt). A first comment or reply CTA is allowed only when the selected publisher can create and verify it. Otherwise keep required links and install commands in the root copy.

Measure reach, engagement, clicks and business outcomes separately. Missing metrics are unavailable, not zero. Authentication and delivery errors do not establish poor content performance.
