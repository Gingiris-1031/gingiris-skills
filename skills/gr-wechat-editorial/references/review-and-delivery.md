# 双重审核与故障处理

## 内容审：意义与真实性

- 标题与正文一致；没有把相关性写成因果、收入写成利润、展示案例写成付费客户。
- 每个关键事实有可定位来源；真实引语保持说话人和上下文。转发者不自动是被引用观点的作者。
- 不通过虚构时间、地点、感受或对话制造“亲历感”。摘要和来源索引不独立证明原始事件。
- 私有素材使用权限与脱敏粒度一致；客户或嘉宾说过不等于同意公开。
- 文风根据用户样本判断；机械括号/破折号/数字配额不是质量标准，套路措辞仅作修改建议。

## 终审：可见结果

- 逐项核对标题、作者、摘要、封面、正文顺序、图片、链接、文末引导。
- 私有注释在本地移除，不能依赖平台自动过滤。内部 source-map.md 单独保存，不上传。
- 简单 inline CSS；手机预览长标题、中文标点、表格横向溢出与段落间距。
- 不自动声明原创；根据真实权利和转载要求在后台设置。
- 草稿响应包含 ID 后再读目标草稿；正文文本一致不代表视觉排版已验证，两者分别记录。

## 来自源 SOP 的故障教训

| 症状 | 应检查什么 | 完成信号 |
|---|---|---|
| 中文变成字面量反斜线 u 转义 | 编码、是否二次 JSON 编码、请求与回读值 | 中文在解析值与后台显示一致 |
| 段落拥挤/样式丢失 | inline CSS、平台过滤与手机预览 | 最终草稿可读，不仅本地 HTML 好看 |
| 出现编造亲历细节 | 回到原始素材与发言人，不用 AI 互相背书 | 删除或改成明确分析，内容复审通过 |
| 上传后结果不明 | 已有草稿ID、列表、时间与正文版本 | 确认现存对象后才决定是否重试 |
| 图片占位或封面错误 | 本地素材、上传结果、草稿引用及实际展示 | 目标草稿封面/正文图片均可见 |

合法 JSON 中的 Unicode 转义本身可以正确解码；不能把源 SOP 的个案推断当成“所有 json= 请求必乱码”。UTF-8 + ensure_ascii=False 有助于可读性，但仍需回读验证。

## 传输边界

本 Skill 不打包旧脚本。对接当前工具时只做所需动作，保留 TLS 验证、超时与错误处理；凭证不写进文章/日志，不打印 token。不要把发布失败自动降级成群发，也不要用无关账号测试。缺封面时说明缺口，不上传空白图凑成功。

发布批准后正文/标题发生实质修改，应按实际授权范围重新定稿；不要将旧稿批准套到新稿。发布与通知粉丝是两个动作，各有结果记录。
