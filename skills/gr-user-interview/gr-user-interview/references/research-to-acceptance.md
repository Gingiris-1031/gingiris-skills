# From an interview to a verifiable product change

Use when a team has many feedback notes but cannot tell engineering what to change. Preserve the source context and distinguish what the user did, what they said, and the team's proposed solution.

## Decision handoff

`Evidence / timestamp | User role and task | Observed blocker | Proposed solution | Benchmark | Core / onboarding / commercial | Priority and rationale | Owner | Acceptance steps | Follow-up user and date`

Acceptance needs a starting state, user action and observable outcome. “Improve onboarding” is not enough. For example: a new test account imports its sample document, completes the target task and can locate the saved result; record the actual result and failures. This is an illustrative acceptance pattern, not a past customer outcome.

Use a short shared document to align product and engineering. A competitor complaint is input; the team still needs to propose a solution and test it. Prioritize by blocked user value and dependency rather than how often a person repeats a request. Revisit the same user after a change where possible; shipping alone does not prove the problem was solved.

## Feedback intake

Keep bug reports and feature requests in separate views of one shared log:

`Date | Reporter / source | Description | Reproduction or current workaround | Screenshot / recording where appropriate | Suggested priority | Owner | Status | Follow-up evidence`

Label suggested priority separately from the team's delivery commitment. Share only the account details and recordings needed for diagnosis, with suitable access controls. Public skill packages must not contain customer transcripts or private evidence URLs.
