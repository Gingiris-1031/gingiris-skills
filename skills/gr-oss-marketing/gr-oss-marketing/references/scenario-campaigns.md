# Scenario campaigns after launch

Use after an initial launch when unrelated posts no longer explain which user job or channel converts. Pick a focused use case and a target audience, then coordinate owned posts, relevant creator/UGC content and permitted community distribution around it. A week can be a useful planning window; choose cadence from production and support capacity rather than treating weekly volume as a universal rule.

## Campaign card

`Scenario | Target user/job | Desired conversion event | Owner | Content and channel sequence | Campaign/source identifiers | Baseline | Observation window | Results and unknowns | Continue / change / stop`

Keep a shared campaign identifier and distinct source/content tags so the theme is comparable without merging channels. Use the existing 2h/24h/72h/7d views where suitable. Set targets from the product and baseline; example impression, signup and star counts are not guaranteed outputs. Review the downstream event, cost and evidence quality, not exposure alone. Community rules and affiliation disclosures still apply; this is not permission for unsolicited bulk outreach.

## Web and CLI measurement readiness

Before reporting the existing launch funnel, record for each surface:

`Start / core-task success / repeat use / paid event | Definition | Data source | Test result | Internal traffic exclusion | Cohort window | Identity coverage | Missing data`

Verify that a success event means a completed useful task and that retries do not double count. Separate Web and CLI populations if identities cannot be reliably linked. If only Web is instrumented, state the CLI blind spot. Missing metrics remain data unavailable, not zero, and stars or downloads cannot substitute for activation. Collection should respect product privacy choices; mandatory CLI registration is not a universal prerequisite.
